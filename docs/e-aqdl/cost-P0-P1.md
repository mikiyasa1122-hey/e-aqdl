# 低コスト化 P0・P1: 調査・仕様差分・テスト計画・結果

修正案（2026-11-02「E-AQDL 低コスト化・品質維持のための修正案」）のうち、P0（計測）と P1（流れを変えずに重複を削る）だけを扱う。P2（リスク別の工程選択）は別の PR にする。

## 1. 調査: トークンはどこで使われているか（実測）

過去の実 run 4件の担当ごとの使用量です（Claude Code の会話記録の usage、モデルは Claude Sonnet 5.5）。

- 「入力」には、キャッシュ読込と書込を含みます。
- 統括の数字は、旧版の集計（会話全体）によるものです。

| run | 要求分析 | 設計 | 実装 | レビュー | 統括 |
|---|---|---|---|---|---|
| 実験03 ③（新規アプリ、52分） | 入力 1.2M・5回 | 0.47M・3回 | **7.3M**・2回 | 0.92M・3回 | **7.5M** |
| 実験03 ④（新規アプリ、37分） | 0.64M・4回 | 0.24M・1回 | **7.8M**・1回 | 0.67M・1回 | **4.0M** |
| 実験05 ③（仕様変更、20分） | 0.24M・3回 | 0.24M・2回 | 1.4M・2回 | 0.39M・2回 | **3.4M** |
| 実験08 a1b（既存リポジトリへの機能追加、8分） | 0.09M・2回 | 0.08M・1回 | 0.84M・2回 | 0.21M・2回 | **2.2M** |

分かったことは次のとおりです。

- **入力の 95% 以上はキャッシュ読込です。** 料金はキャッシュ書込・出力より安いので、トークン数と実費は比例しません。そのため P0 では、課金区分を分けたまま記録します。
- **統括と実装担当で大半を占めます。**
  - 実験08 a1b の統括は、API 呼び出しが33回でした。1回あたりの文脈は 43k〜85k トークンで、Claude Code 本体・Skill・それまでの会話が含まれます。
  - 統括の費用は「基本の文脈 × 呼び出し回数」でほぼ決まります。エンジンの出力そのものは合計 15k 文字ほどでした。
- **引き継ぎ情報（brief）は 1回 4〜6k 文字です。**
  - サブエージェントの文脈に残るので、毎回の API 呼び出しで読み直されます。
  - brief のうち 35〜45% は Role Profile の本文でした。
  - 一般的な決まりには、エージェント定義（agents/*.md）と重なる部分がありました。
- **Quality Gate の時間は小さいです**（7.8〜348秒）。E2E が重いプロジェクトでは効く可能性があります。
- **費用を大きく左右しているのは、サブエージェントの起動回数と仕様の差し戻しの回数です。**
  - 例: 実験03 ③では要求分析が5回、設計が3回、レビューが3回起動しました。
  - これは工程の選び方の問題で、P2 の範囲です。P1（流れを変えない）で減らせる量は限られます。

## 2. 仕様差分

### P0: 計測（`metrics --json`、既存の項目はそのまま残す）

| 追加 | 内容 |
|---|---|
| `schema` / `engine_version` / `token_source` / `token_note` | 形式の版、エンジンの版、使用量の出どころ（Claude Code の会話記録） |
| `stages[]` | 担当・工程ごと（requirements / design / implementation / review / gate / counterfactual / memory）の起動回数・所要時間・トークン・`usage_complete` |
| `roles.*.calls_with_usage` / `calls_without_usage` | 使用量を取得できた起動・できなかった起動の数 |
| `orchestrator_tokens` | 統括の使用量。**run の期間（created〜closed_at）だけ**を数える（旧版は会話全体で、同じ会話の別の run を混ぜていた）。時刻のない行は判定できないので数え、件数を `untimed` に残す |
| `orchestrator_tokens_session` | 統括の使用量（会話全体。init や Skill の読み込みを含む） |
| `tokens_total` / `tokens_complete` | 合計と、全担当・統括の使用量がそろっているか。そろっていなければ合計は下限 |
| `models` | 会話記録にあるモデル名 |
| トークンの各値の `api_calls` | API 呼び出しの回数。同じ呼び出しが複数行に分かれても1回と数える。旧版で記録した分は不明（null） |
| `rework` | gate の不合格、レビューのやり直し、修正ループ、担当ごとの再起動 |
| `quality` | 未検証の数（証拠不足・失効）、人の判断で未確認の数。`external_acceptance_pass_rate` と `critical_defects` は**常に null**（外部の評価器で付ける。エンジンは算出しない） |
| `metrics --runs` | 工程・モデル・入力トークン（キャッシュ含む）・出力トークンの列を追加。旧版で保存された metrics は再集計する |

取得できない値は null（表示は「取得できず」）にして、0 と区別します。料金への換算はしません（料金表は持ちません）。会話の本文は記録しません。

反証テストの実行記録には、所要時間（`sec`）を加えました。

### P1: 流れを変えずに重複を削る（既定はすべて無効）

新しい設定は `cost_optimization` です。既定値のままなら設定の指紋に含めないので、進行中の run に影響しません。

| 設定 | 内容 | 省かないもの |
|---|---|---|
| `compact_handoff` | 引き継ぎ情報から2つを省きます。1つは、エージェント定義と重なる一般的な決まり（言語・state.json・人間への質問・終了時の検証）と、実装担当の手順・禁止事項の一般論です。もう1つは、追加の専門性の Role Profile のうち「責務・成果物・引き継ぎ条件」の節です | 次のものは省きません。<br>・run 固有の情報（仕様・設計の場所と指紋、修正依頼、未設定の検証、要求、チェック）<br>・工程の Role Profile の全文<br>・追加の専門性の判断基準・禁止事項・検証条件<br>・レビュー担当と要求分析担当の手順 |
| `gate_fail_fast` | 前のチェックが不合格なら、後ろの重いチェック・検証（integration・e2e）を実行しません | 実行しなかったものは「未実行」（不合格）として記録し、合格にはしません。gate は前の不合格で不合格のままです |

あわせて、エージェント定義（agents/*.md）の「守ること」に共通の決まりを書き足しました。`compact_handoff` で引き継ぎから省いても、同じ内容がエージェント定義に残ります。

実行時の設定は `config()` が毎回複製を返すように直しました。呼び出し側の変更が既定値に漏れないようにするためです。

### やっていないこと（理由）

- **中間チェックの結果の再利用はしていません。** 実測では gate の時間が小さく、効果に比べて「古い結果の再利用」の危険のほうが大きいと判断しました。
- **修正ループの早期停止は入れていません。** 流れが変わるので P2 で扱います。
- **統括の呼び出し回数を減らす変更はしていません。** 影響は最大ですが、手順（Skill）の変更になります。

## 4. 変更前後の比較

- 引き継ぎ情報の長さを比べました。実験08 a1b の状態で、4担当の合計は 18,702 文字から 16,332 文字に減っています（−13%）。
  - 担当ごと: 要求分析 −9%、設計 −9%、実装 −20%、レビュー −13%

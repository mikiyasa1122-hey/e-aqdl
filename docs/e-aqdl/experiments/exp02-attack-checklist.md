# 攻撃役のチェックリスト（実験02）

対象の成果物を起動し、実際にリクエストを送って確かめる。コードは API の使い方を知るためだけに読んでよいが、
判定は必ず実際のリクエストと応答で行う。推測だけで「脆弱」「安全」と書かない。

各項目の判定: 防げた / 防げなかった / 該当しない（その機能がない） / 確かめられなかった（理由を書く）
「防げなかった」には、再現手順（送ったリクエストと返った応答）を必ず書く。

| # | 項目 | 確かめ方の例 |
|---|---|---|
| A1 | 認証なしのアクセス | 認証情報なし・不正な認証情報で、一覧・取得・作成・更新・削除を試す |
| A2 | 他人のメモの閲覧（IDOR） | メンバー2人を用意し、相手のメモの ID を指定して取得・一覧で見えるか |
| A3 | 他人のメモの更新・削除 | 相手のメモの ID を指定して更新・削除できるか |
| A4 | 権限の昇格 | メンバーが管理者用の操作（全件の取得・他人のメモの管理・利用者の管理など）をできるか。リクエストの本文で role や owner を指定して書き換えられるか |
| A5 | 存在の漏えい | 存在しない ID と、見えない他人の ID で応答が違うか（違えば「防げなかった」ではなく「注意」と書く） |
| A6 | 入力検証 | 空・巨大（1MB 以上）・型違い・不正な JSON を送って、500 や異常終了にならないか |
| A7 | 二重送信 | 同じ作成リクエストを連続・同時に送ったときの扱い（重複防止の仕組みの有無を記録。仕組みがなくても仕様違反とはしない） |
| A8 | 資格情報の扱い | パスワードがあるなら平文で保存していないか。トークンが推測可能でないか。資格情報がソースに直書きされていないか |
| A9 | エラーで内部情報を漏らさない | 例外を起こす入力でスタックトレース・パス・SQL が返らないか |
| A10 | インジェクション | DB を使う場合、SQL インジェクション。そのほかシェル・パス・テンプレートへの注入 |
| A11 | 起動のしやすさ・説明 | README などで起動方法・利用者の作り方が分かるか（分からなければ攻撃の前提を書く） |

最後に、重大な問題（他人のデータの閲覧・改ざん、権限の昇格、認証の迂回、資格情報の漏えい）を一覧にする。

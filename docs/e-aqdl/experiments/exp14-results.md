# 実験14: 差分の品質（変えたファイルだけの Lint・差分カバレッジ）の効果

PR #10（0.6.6）の効果を、変更前のエンジン（PR #9 の 0.6.5）と比べた。各3回、計6回。モデルは Claude Sonnet 5.5、依頼者役は隠れた意図を持つ別の Claude で、これまでと同じ仕組み。

- **お題**: 在庫リポジトリ（実験04 と同じ）に `export_low_stock_csv(items, threshold=10)` を足す。仕様はお題の文にすべて書いた（並び順・見出し・改行・CSV の引用・ValueError）。
- **仕掛け**: リポジトリに、テストのない古いファイル `inventory/report.py` を置いた。ここには ruff の警告が5件ある（未使用の import、bare except など）。`pyproject.toml` で ruff を設定し、README には「Lint: `ruff check`」とだけ書いた。古い警告があることは書いていない。
- **変更前（before）**: エンジン 0.6.5。設定は `workflow.mode: auto` だけ。
- **変更後（after）**: エンジン 0.6.6。`quality.diff_coverage` を有効にした（レポート `coverage/coverage.json`、基準 80%）。
- **評価**: 作り手から独立に、終了後に測った（`harness/evaluate14.py`）。
  - 変えたファイルの新しい Lint の警告
  - 既存ファイルの変更
  - 差分カバレッジ（coverage.py で測り直し、起点のコミットとの差分の行で数える）
  - 隠し受け入れテスト7件（参照実装で全件合格、境界・改行・並び順を間違えた実装で3件不合格になることを先に確かめた）

## 人への返答が増えた理由（before）

before の余分な返答は、すべて次の2つのどちらかだった。

| | 古い Lint の警告で仕様が矛盾し、人に判断を求めた | 承認の返答が質問 ID に触れていて、承認として扱われなかった |
|---|---|---|
| before-1 | +2 | +1 |
| before-2 | +1 | +1 |
| before-3 | +2 | +1 |
| after（3回） | 0 | 0 |

- **古い Lint の警告**（PR #10 が狙ったもの）は、before の3回すべてで起きた。
  - 仕様の受け入れ条件は「`ruff check` が通る」、対象外は「`report.py` は変えない」で、この2つが矛盾した（`ruff check .` は前からある5件で必ず失敗する）。
  - 実装担当は、Lint の対象を手で絞って gate を通した。before-1 では、レビュー担当がこれを「承認のない検証条件の弱体化」と指摘し、人への判断の依頼と仕様の改訂・再承認になった。before-2 と before-3 は、実装の後に統括が人へ判断を求めた。
  - after では一度も起きなかった。after-1 と after-3 は `{changed:.py}` を使った。
  - after-2 は理由が分からない。仕様は before と同じく「ruff check が通る」（範囲の指定なし）で、実装担当も before と同じく対象を手で絞った。それでも、レビュー担当も統括も人に判断を求めなかった。
    - 考えられるのは、after のレビュー担当には「Lint の指摘は機械に任せる」という指示が入っていたこと。もしこれが効いたのなら、「検証の範囲を承認なしに狭めた」という正当な指摘まで抑えてしまうおそれがある。1回だけなので判断できない。
- **質問 ID への言及**は PR #9（判断シート）の規則による。PR #10 とは関係がない。
  - 依頼者役が「Q1〜Q3 は推奨案でお願いします。承認 SPEC-…」と返し、エンジンが「推奨と違う回答の可能性がある」として承認にしなかった。推奨どおりと書いているのに止めるのは、規則が厳しすぎる。
  - たまたま before にだけ起きたので、上の差の一部（返答1回ずつ）はこれによる。これを除いても、返答の平均は 2.7 回 対 1.0 回。

## 分かったこと
- **品質は両方とも同じだった。** 隠しテストは全件合格し、新しい Lint の警告は0件、`report.py` は一度も変えられず、変えた行の差分カバレッジは独立に測って6回とも100%。
- **効いたのは「変えたファイルだけ」を最初から仕組みにしたこと（3回中2回）。** 古い問題があるリポジトリでは、全体の Lint を条件にすると仕様が矛盾し、実装担当の回避策 → レビューの指摘 → 人への判断の依頼、という往復が生まれた。`{changed:.py}` を使った after-1・after-3 では、それが起きなかった。after-2 で起きなかった理由は分からない（上記）。
- **差分カバレッジの gate は、このお題では結果を変えなかった。** 変更前もテストで変更行をすべて実行していた（100%）。小さな関数の追加では、今のモデルは十分なテストを書く。差分カバレッジが効くのは、テストの書きにくい変更（分岐の多い既存コードの修正など）だと考えられるが、まだ確かめていない。

## 限界
- 1題・各3回。費用の差のうち一部は、PR #10 と関係のない承認の拒否による（上の表）。
- 古い Lint の警告がある、という仕掛けは意図的に置いたもの。古い問題のないリポジトリでは、変更前との差は出ないはず。
- 差分カバレッジの効果は、このお題では測れなかった（変更前も100%）。

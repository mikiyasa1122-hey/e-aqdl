# 実験11: リスクに応じた工程の選択（workflow.mode）の効果

既存の在庫 API クライアント（実験04 と同じリポジトリ）に、低リスクの小さな機能を足すお題を2つ用意した。
- a: `fetch_items` に、在庫の少ない順に並べ替える `sort` 引数を足す
- b: 在庫の一覧を CSV 文字列にする `to_csv(items)` を足す

各お題で、`workflow.mode` を `full`（従来どおり全工程）と `auto` の2条件で比べた。各条件3回、計12回。
依頼者役は隠れた意図（本物の API にはつながらない、test_live を変えない、細部はお任せ）を持つ別の Claude が務めた。
モデルは Claude Sonnet 5.5、エンジンは 0.6.4（e6b4900）。

| お題 | 条件 | 選ばれた工程 | 費用（3回） | 平均 | 時間の平均 | 担当の起動 |
|---|---|---|---|---|---|---|
| a | full | strict | $2.42 / $3.55 / $3.20 | $3.06 | 332秒 | 要求2・設計1・実装1・レビュー1 |
| a | auto | standard（3回とも） | $1.33 / $2.10 / $1.45 | **$1.63（−47%）** | 259秒（−22%） | 要求2・実装1・レビュー1 |
| b | full | strict | $1.53 / $3.49 / $3.75 | $2.92 | 376秒 | 要求2〜3・設計1〜2・実装1〜2・レビュー1 |
| b | auto | standard（3回とも） | $3.14 / $1.47 / $4.72 | $3.11（+6%） | 303秒（−19%） | 要求2〜3・実装1・レビュー1 |

12回の全体では、full の平均 $2.99 に対して auto は $2.37（−21%）、時間は −20% だった。

## 品質
- 12回すべてで、gate は合格した。
- 機能を外から確かめる簡単なチェック（並べ替えの順序、CSV の中身と引用符）も、12回すべて合格した。
- テストの失敗は、どの回も本物の API に接続する `test_live` だけで、これはこの環境では必ず失敗する。
- a-full-3 は、`test_live.py` に並べ替えの live テストを1件追加していた。依頼者の意図は「test_live を変えない」で、既存の行は消していないが、意図には反する。

## 分かったこと
- auto は、低リスクのお題で6回とも standard を選んだ（設計担当を省いた）。lite は一度も選ばれていない。理由は、要求分析担当が主要な要求に必ず「重要」の印を付け、その印があると lite に行けない規則にしていたこと。この規則では、lite は実質的に選ばれない。
- 費用の差は、お題 a ではっきり出た（−47%）。お題 b では出ていない（+6%）。b-auto-3 は人への返答が6回あり（他は2〜4回）、$4.72 かかった。前回と同じく、費用は人とのやりとりの回数で大きくぶれる。
- 過去の実 run 10件（メモ共有 API・仕様変更・Slack 通知・マイグレーション）を判定にかけると、すべて strict だった。認証・権限・秘密・削除・スキーマを含むので、妥当な判定である。auto で費用が下がるのは、低リスクのお題に限られる。

## 限界
- 各条件3回で、ばらつきが大きい（同じ条件で $1.47〜$4.72）。
- 品質は簡単な機能チェックだけで見ており、検査役による採点はしていない。

# 比較実験 03: 仕様が依頼者の意図どおりになるか

お題（全条件同じ）: 「チームで使うメモ共有の Web API を Python で作ってください。メンバーは自分のメモを書けて、管理者は全員のメモを管理できるようにしたいです。」
依頼者の隠れた意図 I1〜I8（共有の既定・非公開・自分のメモだけ編集・管理者は編集不可・自己登録なし・ゴミ箱と復元・文字数・検索）。
依頼者役（別の Claude）は、聞かれたことにだけ答え、仕様の承認を求められたら意図と照らして指摘する。
検査役は条件名を伏せたまま実際に起動して I1〜I8 を判定。各条件1回。

| 条件 | 人とのやりとり | 意図どおり（8点満点） | 時間 | 費用 |
|---|---|---|---|---|
| ① 普通 | なし | 3 | 1.5分 | $0.28 |
| ② テストを書いて | なし | 2 | 1.3分 | $0.22 |
| ⑤ 曖昧なら作る前に質問して | 作る前に6問、1往復 | 8 | 2.8分 | $0.54 |
| ③ E-AQDL Memory なし | 9往復（質問・仕様の差し戻し・再承認） | 8 | 52分 | $34.18 |
| ④ E-AQDL Memory あり | 6往復 | 8 | 37分 | $17.82 |
| 参考: ①＋依頼者が完了報告を読んで直させる | 4往復 | 8 | 4.6分 | $2.64 |

## 注意
- 依頼者役が聞かれていない意図まで答えた場面がある（④の最初の回答、参考枠の①）。参考枠の①はこの不具合で生まれたが、「人が報告を読んで直させる」現実的な流れとして残した。規則を厳しくした後の①が本来の①。
- ③は依頼者役が仕様の承認時に「検索・最初の管理者・文字数上限」の漏れを指摘して差し戻した。E-AQDL の承認の場が働いた例。
- ⑤も③④も満点のため、意図どおりかでは差がつかない。差は費用（60〜120倍）と、③④が加えた検証（テスト数百件、独立レビュー、仕様と証拠の対応表）。
- 各条件1回。お題は1つ。

## 結論（傾向）
- 意図どおりになるかを決めたのは「作る前に曖昧な点を人に聞くか」。①②は聞かずに作り、5〜6項目を外した。
- 聞かせる仕組みとしては、プロンプトに一文足すだけ（⑤）で今回は十分だった。E-AQDL の質問・仕様承認も同じ結果に届いたが、費用は大きい。
- E-AQDL の価値を主張するなら、「意図どおり」以外の軸（後から追える証拠、変更時の再承認、長い開発での漏れ）で示す必要がある。

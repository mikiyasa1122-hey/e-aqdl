# 欠陥検出ベンチマーク（PERF-01）の手順と数え方

**完成したコードの品質**（受け入れテストに通るか）と、**独立レビューの検出能力**（欠陥を見つけるか）を分けて測るためのベンチマークです。このベンチマークが測るのは後者だけです。

## 1. 何を測るか

- 対象: E-AQDL の独立レビュー担当（`plugins/aq-dlc/agents/reviewer.md`）
- 入力: エンジンが SubagentStart で返す、本物の引き継ぎ情報
  - 各ケースは、エンジンで実際の run として「仕様の承認 → 設計 → 実装 → gate の合格」まで進める。
  - そのうえでレビュー担当を起動したときの文面を、そのまま渡す。
- 測らないもの（`not_measured`）
  - 実装の品質
  - 人への確認回数（レビュー担当だけを動かすため、人とのやりとりがない）
  - counterfactual・holdout・差分カバレッジを有効にした条件

## 2. ケース

- **対象アプリ**（`app/`）: 組織ごとのメモのライブラリ（Python・SQLite）。認可・入力検証・楽観的ロック・トランザクション・回数の制限・署名付きリンクを持つ。
- **仕様・設計**（`run_docs.py`）: 全ケースで共通。
- **欠陥ケース（30件）**: 参照コードに欠陥を1つずつ入れたもの。分類と件数は次のとおり。

  | 分類 | 件数 |
  |---|---|
  | 認可・スコープ | 5 |
  | 入力検証 | 4 |
  | 例外処理 | 3 |
  | 境界値 | 4 |
  | 並行・競合 | 3 |
  | トランザクション | 4 |
  | SQL の組み立て | 4 |
  | 機密情報 | 3 |

  重大度は high 17件・medium 13件。
- **欠陥なしケース（10件）**: 振る舞いを変えない変更（名前の変更・関数の抽出・順番の入れ替えなど）。
- **各ケースの記録**（`cases.py`）: `case_id`・分類・重大度・題名・箇所・原因・影響・置き換え（ファイル・元・先）・再現テスト。
- **機械による確認**（`check_cases.py`）
  - 参照コードでは、見えるテストとすべての再現テストが合格する。
  - 欠陥ケースでは、見えるテストは合格し（gate を通る）、そのケースの再現テストは失敗する。
  - 欠陥なしケースでは、見えるテストとすべての再現テストが合格する。
- **見えるテスト**（`app/tests/`）は、欠陥の箇所をわざと確かめていない（確かめると gate で止まり、レビューまで届かないため）。
  - そのため、どのケースでも「テストが足りない」という指摘が出る。これは `test_gap` として、コードの欠陥の指摘（TP・FP）とは別に数える。

### 参照コードの校正（評価の前に一度だけ）

- 参照コードに実在する欠陥が残っていると、欠陥なしケースが欠陥なしではなくなる。そのため、評価の前に、欠陥なしケースと1件の欠陥ケースで試しにレビューした（計6回）。
- 見つかった参照コードの実在の欠陥は直し、仕様のあいまいな点は書き足した。

  | 回 | 直したもの |
  |---|---|
  | 1回目 | 共有リンクの非 ASCII の署名・移管の対象の読み出し・tags と page の型・非公開と管理者の関係 |
  | 2回目 | 接続の共有・閲覧の TOCTOU・短い api_key・リンクの形の検査 |
  | 3回目 | 改行・他の数字を通す正規表現・COMMIT の失敗・検索のタグの個数・set の tags |

- この6回は評価に使っていない。評価は、校正の後に全40ケースを新しく作り直して行う。
- それでも参照コードに欠陥が残っている可能性はある。指摘が実在の欠陥（`real_other`）か誤検知（`false_positive`）かは、判定役と手での確認で分ける。

## 3. 実行

```
python3 bench/review/check_cases.py                         # ケースの妥当性（必ず先に）
python3 bench/review/run_bench.py build  --out DIR          # 40ケースを run としてレビューの直前まで進める
python3 bench/review/run_bench.py review --out DIR --parallel 3 [--rep N]
python3 bench/review/run_bench.py judge  --out DIR
python3 bench/review/run_bench.py report --out DIR          # report.md・summary.json
```

- **レビュー担当の起動**: `claude -p "<引き継ぎ情報>…" --append-system-prompt <reviewer.md の本文> --tools Read,Grep,Glob,Bash --dangerously-skip-permissions --output-format json`
  - 作業フォルダは、そのケースの run のプロジェクト。
  - `AQDLC_HOME` は、その run のもの（引き継ぎ情報の `trace`・`history` を使えるようにする）。
- **プラグインの hook なしで動かす点**: そのため、hook が担う制限は次のように置き換えている。
  - 書き込みの禁止: Write / Edit をツールから外す。レビューの後にファイルが変わっていたら、その回は無効にする。
  - ブラインドレビュー（実装報告を読めない）: 作業フォルダから impl.md を外す。
- **判定役**: 正解・仕様・コード・レビューの報告を渡した別の `claude -p`（ツールなし）。各指摘を分類する。
- **記録する条件**（`conditions.json`）: リポジトリのコミット・エンジンのツリー・Python の版・設定。モデルは各回の結果（`models`）に残る。

## 4. 数え方

| 分類 | 意味 | 数える先 |
|---|---|---|
| matches_defect | 埋め込んだ欠陥そのものを指摘（同じ箇所で、原因か影響が一致） | TP |
| real_other | 埋め込んだもの以外の、実在する欠陥 | 別に表示（TP にも FP にも入れない） |
| test_gap | テストの不足・弱さだけの指摘 | 別に表示 |
| style | 好み・保守性の提案 | 別に表示 |
| false_positive | 欠陥でないものを欠陥と指摘 | FP |
| ambiguous | 判定役が決められない | 手で決める（`adjudication.json`）。決めていないものは数えず、件数を出す |

- **TP**: 欠陥ケースで、埋め込んだ欠陥を指摘した回数。
- **FN**: 欠陥ケースで、指摘しなかった回数。判定役の `partial`（箇所に触れたが原因・影響が違う）は、手で yes / no に決める。
- **FP**: false_positive の指摘の数。欠陥ケース・欠陥なしケースの両方で数える。
- **計算式**: `precision = TP / (TP + FP)`、`recall = TP / (TP + FN)`
- **あわせて出すもの**
  - 高重大度の Recall と見逃しのケース ID
  - 重大として指摘した Recall
  - 欠陥なしケースで「要修正」と判定した数
  - 1回あたりの費用・時間（平均・標準偏差・最小・最大と、ケースごとの値）
- **ambiguous・partial の手での判定**: `adjudication.json` に理由とともに残す。

## 5. 限界

- 対象アプリは1つで、Python だけ。欠陥は人工的に埋め込んだもの。
- 判定役も Claude である。判定の誤りを減らすため、正解・仕様・コードを渡して分類の規則を固定し、ambiguous と partial は手で確かめる。
- レビュー担当は hook なしで動く（上記の置き換え）。正解（`cases.py`）は同じマシンのリポジトリにあるので、意図的にファイルシステムを探せば読める。今回の記録（`--output-format json`）には使ったコマンドが残らない。そのため確かめられるのは、レビューの報告に正解のファイル（`bench/review`・`cases.py`）への言及がないかだけ。
- 最初の基準値は各ケース1回。ばらつき（同じケースでの再現性）は、`--rep` で回数を増やして測る。

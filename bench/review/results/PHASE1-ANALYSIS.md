## 読み方（正直に書いておくこと）

- **減った誤検知のほとんどは軽微（32 → 2）で、指摘の書き方が変わったことによる。**
  - 例は共有リンクの先頭ゼロ。変更前は「欠陥」として書かれ、14回が誤検知になった（29回は改善の提案として書かれ style）。Phase 1 では34回が「改善提案」として書かれ（style）、誤検知は1回だけだった。
  - 見つけている内容が減ったのではなく、欠陥でないものを欠陥と主張しなくなった。方針書のねらい（改善提案を修正必須と混同しない）どおりの変化だが、「同じ観察を、正しい区分で書くようになった」という意味で読む。
- **重大の誤検知（誤った修正必須）は 6 → 5 で、ほとんど変わっていない。**
  - 「必要な修正だけを求める」の中心である重大の誤検知については、効果は確認できなかった（件数が少なく、差は1件）。
  - Phase 1 の重大の誤検知5件の内容: 移管で updated_at を更新しない、タグの重複の数え方（2件）、「実在する欠陥は確認できなかった」と書きながら重大にしたもの、title・body の読み出しの経路の誤読。
- **重大の指摘の数が減った（4.4 → 3.6）主な理由は、テスト不足の指摘がまとまったこと**（323 → 198）。
  - Phase 1 では、テスト不足を「証拠不足」の [重大] として、根拠（どの受け入れ条件のためか）とともに1〜2件にまとめる書き方になった。
- **欠陥なしケースの「要修正」は、両方とも 30/30。**
  - このベンチマークの見えるテストは、わざと受け入れ条件を確かめていない。そのため、Phase 1 の規則（必須の受け入れ条件の検証がない → 証拠不足 → 重大）では、要修正が正しい判断になる。
  - 正しく合格できるかは、このベンチマークでは測れない。方針書 7.2 の、別のクリーンケース群が必要（未実施）。
- **対応区分は書かれていた。**
  - Phase 1 の指摘のほぼすべてに付いていた（[重大] に付いていないものが2件）。
  - 「証拠不足」の198件は、すべてテスト不足（test_gap）に分類された。
  - 「改善提案」の [軽微] の大半は style だった。ほかに real_other が21件、誤検知が2件。

## 判定の手での確認と、揃えた規則

- 判定役（Claude）が決めきれなかった指摘と、同じ根本原因で回によって分類がぶれた指摘を、両方の条件に同じ規則で揃えた（`../adjudicate_rules.py`、結果は各フォルダの `adjudication.json`）。
  - 揃えたのは、判定役が false_positive・real_other・ambiguous としたものだけ。style と test_gap は変えていない。最初は style も変えてしまい、Phase 1 に不利に数えていたので、やり直した。
  - **認可の判定がトランザクションの外（TOCTOU）** → real_other。参照コードに残る実在の弱点で、削除が通ることを再現した。
    - 最初の規則は「トランザクション」だけを探し、「`transaction()` の外」と書いた指摘を取りこぼしていた。直してから数え直した。
  - **共有リンクの先頭ゼロ** → false_positive。仕様は10進の数字だけを求め、署名は整数で計算するので偽造にならない。ただし、同じ指摘が巨大な page の OverflowError にも触れていれば real_other。
  - **巨大な page の OverflowError** → real_other。
  - 移管で updated_at を更新しない → false_positive。TX-04 の閲覧数の残り → 埋め込んだ欠陥の影響（matches_defect）。
- 規則で自動的に分類を変えたものから、両方の向きを抜き取って読み、規則どおりであることを確かめた。

## 限界

- 対象アプリは1つ（Python）で、モデルは1つ、各ケース3回。小さな標本なので、1件の増減で優劣を決めない。
- 判定役も Claude で、揃えの規則は正規表現による。抜き取りでしか確かめていない。
- 参照コードには既知の実在の欠陥が残っている（v1 の限界。`v0.6.6-baseline/ANALYSIS.md`）。

## 1. 見逃しの原因（保存済みの6回のレビューから）

SQL-02 は、検索語に `_like_escape` を適用していない欠陥（`%`・`_` がワイルドカードになる）。変更前後の6回すべてで見逃していた。

- 6回とも、レビュー担当は「LIKE は ESCAPE 句とプレースホルダーを使っている」と書き、問題なしとしていた。
- コードには `ESCAPE '\'` の句と `_like_escape` の定義が残っている。欠けているのは、**関数の呼び出しだけ**。
- つまり原因は、**「防御の部品があること」を見て「値に適用されていること」を確かめなかった**レビューの手順にある。
  - SQL の文脈の理解の不足ではない（同じレビュー担当が、ESCAPE 句の欠落 SQL-06 は検出する）。
  - 判定役の分類の誤りでもない（レビューの本文に、欠陥への言及がない）。
  - テスト不足は背景にある（見えるテストは検索を確かめていない）が、レビュー担当は「テストがない」とは指摘しており、それでも実装は正しいと読んでいた。

## 2. 変更

レビュー担当の指示（`agents/reviewer.md` と引き継ぎ）の「見逃しを防ぐ確認」に、2行を足した。

- 検証・エスケープ・認可の関数や句は、定義されていることではなく、対象の値に実際に適用されているかを、入力から使われる箇所までたどって確かめる。
- コードに SQL があるときは、LIKE のワイルドカードとエスケープ文字そのものの扱い、ESCAPE 句、プレースホルダー、DB・ORM 固有の意味を確かめる。SQL がなければ不要。

1つのケースに合わせた指示にならないよう、1行目は SQL に限らない書き方にした。
また、同じ種類で壊れ方の違うケースを3件足した（`../sql_cases.py`）。

- SQL-06: LIKE に ESCAPE 句がない
- SQL-07: 本文の条件だけ、エスケープしていない検索語を渡している

## 4. 読み方（正直に書いておくこと）

- **SQL-02 は 0/3 → 2/3 で、まだ1回見逃している。**
  - 見逃した1回は、以前と同じ読み違い（「LIKE のエスケープは確認した」）だった。指示を足しても、必ず確かめるわけではない。
  - 3回ずつの計測なので、2/3 という数字そのものの幅は広い。「検出できるようになった」とは言えるが、「検出率が何%になった」とは言えない。
- **検出した2回のうち1回は、対応区分が「証拠不足」だった。**
  - 指摘の本文には、原因（`_like_escape` を呼んでいない）と影響（`%` だけの検索語が全件に一致する）が正しく書かれている。そのため、数え方（要件 5: 正しい原因と影響が示されたときだけ検出に数える）では検出に数えた。
  - ただし「静的に確認しただけで、再現していない」として、実装の修正ではなく検証の追加を求める区分にしていた。REV-02 の振り分けでは「検証の追加」に回る。足したテストが失敗して欠陥が確かめられる流れにはなるが、区分としては「修正必須」が正しい。
- **追加した3件は、変更前からほぼ検出できていた**（8/9）。
  - つまり、足した観点の効果を示しているのは、実質的に SQL-02 の1ケース（と SQL-05 の1回）だけである。
  - 「欠けているものが目に見える」欠陥（ESCAPE 句がない・片方だけ違う値）は、もともと見つけやすい。SQL-02 のように「部品は揃っていて呼び出しだけがない」欠陥が難しい。
- **欠陥なしケースで、重大の誤検知が1回出た**（変更前は0回）。
  - 内容は共有リンクの先頭ゼロで、足した SQL の観点とは関係がない。以前からある誤検知の種類で、1件の差なので、悪化とは判断しなかった。
  - テスト不足の指摘は増えた（218 → 255）。この題材では見えるテストが薄いので、指摘そのものは正しい（誤検知ではない）。
- **この比較の「変更前」は、Phase 1 より誤検知が少ない**（Phase 1 は 120回で 7、今回の既存40ケースは 4）。REV-01・REV-02 の後のエンジンで測ったため。ただし、条件をそろえた比較ではないので、REV-01・REV-02 の効果とは言わない。

## 読み方（正直に書いておくこと）

- **題材は、完全にはクリーンではなかった。**
  - 1回（CLN-10 の1回目）が、実在する小さな欠陥を見つけた。`list_notes(sort=[])` のようにハッシュできない値を渡すと、ValidationError ではなく TypeError になる（R3「範囲外は ValidationError」に反する）。再現して確かめた。
  - レビュー担当は、これを「改善提案」の [軽微] にして、判定を「合格」にした。仕様に反する欠陥なので、本来は「修正必須」で「要修正」が正しい。つまり、**この1回の合格は、欠陥を軽く扱いすぎた結果である**。
  - 残りの29回は、この欠陥に触れていない。元の参照コード（`app/`）にも同じ欠陥がある。
  - 正解のラベルは変えていない。計測の後に、題材を都合よく直すこともしていない。次の版で、参照コードとテストを直してから測り直す。
- **軽微の指摘の大半は、仕様に反しない観察だった。**
  - 判定役の分類で style が30件。内容は、共有リンクの先頭ゼロ・タグの検査の重複・RateLimiter の記録が増え続けることなど。
  - 既存の40ケースで誤検知の主な原因だった「共有リンクの先頭ゼロ」も、ここではすべて改善提案として書かれた。
- **この題材は、合格させやすい側に寄っている可能性がある。**
  - テストのファイル名とクラスの説明に、受け入れ条件・リスクの ID を書いた。そのため、レビュー担当が対応を確かめやすい。
  - 実際の開発では、テストがここまで整理されていないことが多い。
- **合格率 100% は、レビュー担当が甘くなったことを意味しない。**
  - 欠陥の検出能力は、既存の40ケースと SQL の追加ケースで別に確かめる（同じエンジンで計測中。`eval02-*` の結果を参照）。
  - クリーンケースの合格率と欠陥の検出率は、組で読む。

## 限界

- 題材は1つ（Python・SQLite のライブラリ）で、書き換えは振る舞いを変えない小さなものだけ。各ケース3回。
- 判定役も Claude。重大の指摘が0件だったため、判定役の分類が合否に影響したのは上の1件だけ（real_other。手で再現して確かめた）。
- レビュー担当は、ベンチマークでは hook なしで動く。報告の形式が不正なときの書き直し（REV-01）は、実際の run では起きるが、ここでは起きない（不正は0件だった）。

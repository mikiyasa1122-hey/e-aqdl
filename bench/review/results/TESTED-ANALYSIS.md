# 「検証あり・欠陥あり」のケース群と、レビューの指示の追加（不採用）

## 何を確かめたか

全工程の比較の試行（`bench/workflow/results/pilot`）で、自作のテスト82件がすべて合格している実装に対して、独立レビューが実在の欠陥3種類を見逃して「合格」にした。そこで、次の2つを確かめた。

1. テストが揃って合格しているとき、レビュー担当は欠陥を見逃しやすいか。
2. レビュー担当の指示に3行足すと、見逃しが減るか。
   - テストがすべて合格していても、欠陥がない証拠にはならない。
   - テストが確かめていない入力・状態・順序を考えて、コードで確かめる。
   - 仕様に反する挙動は、テストの有無にかかわらず「修正必須」にする（改善提案に下げない）。

## ケース群

`../tested_cases.py` の12件。参照コード（`app_clean`）に欠陥を1つ入れ、その欠陥で失敗するテストのメソッドだけを取り除いた（残りは 56〜62件で、すべて合格する）。受け入れ条件ごとのテストのファイルは残るので、検証は揃って見える。

- TD-01〜03: 試行で残った3種類（認可の確かめ直しがない・巨大な page・更新で古い行の値を使う）
- TD-04〜12: 既存の40ケースから9件（認可・例外・境界値・並行・トランザクション・SQL・機密情報・入力検証）
- 確認: `python3 bench/review/check_cases.py --set tested`
- 取り除いたテストは、各フォルダの `dropped_tests.json`。同時の操作の欠陥は、テストが毎回は失敗しないので、4回実行して1回でも失敗したものを取り除く。

## 条件

- 変更前: エンジンのツリー eab96dd（`review/eval02-sql-guidance`。今の main と同じ）
- 変更後: エンジンのツリー 7cb359c（`review/passing-tests-not-proof`。変更前 + 上の3行）
- 12件 × 各3回。クリーンケース群（10件 × 3回）は変更後だけ測った（変更前は `eval01-clean-after/` の結果を使う）。
- **モデルは Claude Sonnet 5.5**（これまでの計測と同じ）。測った日は 2026-11-11〜16。

### モデルを取り違えた計測（参考として残す）

最初の計測は、レビュー担当と判定役が **Claude Opus 5.5** で動いていた。`run_bench.py` がモデルを指定しておらず、`claude` の既定のモデルが変わっていたため。集計のとき、1回の費用が約4倍（$0.13 → $0.51）になっていることから気づいた。

- `run_bench.py` に `--model`（既定は `claude-sonnet-5-5`）を足し、条件に記録するようにした。
- Opus の結果は各フォルダの `opus/` と `tested-compare-opus.md` に残した。これまでの数字とは比べられない。
- `conditions.json` はケースを作ったときのもので、モデルの欄がない。使ったモデルは、各レビューの記録の `models` にある。

## 結果（Sonnet 5.5）

| 指標 | 変更前 | 変更後（3行を追加） |
|---|---|---|
| 欠陥を指摘した回（重大・軽微のどちらでも） | 33/36 | 31/36 |
| 欠陥を「修正必須」の重大として指摘した回 | 31/36 | 29/36 |
| 欠陥があるのに「合格」にした回 | 5/36 | 6/36 |
| 誤検知 | 0 | 0 |
| 1回の費用・時間 | $0.122・27.1秒 | $0.116・28.2秒 |
| クリーンケース群の合格 | 30/30 | 27/30 |

- 見逃し・合格が集中したのは2件。
  - **TD-03（更新で、変えない欄を古い行から取る）**: 変更前後とも、3回すべて「合格」。指摘した回も「改善提案」に下げていた。
  - **TD-10（検索語にエスケープの関数を適用していない。SQL-02 と同じ欠陥）**: 変更前は 2/3 で検出、変更後は 0/3。
- クリーンケース群で止めた3回は、すべて `sort=[]` で TypeError になる実在の欠陥（R3 に反する）を「修正必須」にしたもの。重大の誤検知は0件。

## 結論: 3行は採用しない

- **足した3行で、見逃しは減らなかった。** 33/36 → 31/36 で、差は誤差の範囲だが、少なくとも改善はしていない。TD-10 は逆に検出が減った（3回ずつなので、指示のせいとは言えない）。
- **1つめの問い（テストが揃うと見逃しやすいか）は、部分的に当てはまる。**
  - 12件中10件は、テストが揃っていても、変更前から毎回検出していた。
  - 見逃すのは「部品はあるが使い方が違う」型（TD-03・TD-10）で、テストの有無より、欠陥の型の問題と見たほうがよい。SQL-02 と同じ傾向である。
- **3行目（仕様に反する挙動を改善提案に下げない）には、効果の兆しがある。**
  - `sort=[]` の欠陥は、変更前は30回中1回だけ見つけ、それも改善提案にして合格にしていた。変更後は3回見つけ、3回とも修正必須にした。
  - ただし TD-03 では、変更後も改善提案に下げていた。件数が少なく、採用の根拠には足りない。

`review/passing-tests-not-proof` のブランチは、マージしない（PR も出さない）。

## Opus 5.5 での結果（参考）

| 指標 | 変更前 | 変更後 |
|---|---|---|
| 欠陥を指摘した回 | 36/36 | 35/36 |
| 欠陥があるのに「合格」にした回 | 2/36 | 1/36 |
| クリーンケース群の合格 | 未計測 | 13/30 |
| 1回の費用 | $0.51 | $0.52 |

- Opus は、指示を足す前から12件すべてを検出した。
- クリーンケース群で止めた17回の重大の指摘25件は、判定役がすべて実在の欠陥と分類した。内容は2つ。
  - `update_note` の `version` に文字列（`"1"`）を渡すと、SQLite が数値として比べて更新が確定し、その後 `version + 1` で TypeError になる（例外なのに変更が残る。R10 に反する）。
  - `sort=[]` で TypeError になる。
- Opus + 指示なしのクリーンケース群は測っていないので、合格が減った原因がモデルか指示かは切り分けていない。

## 分かったこと・次にすること

- **「クリーン」として作った参照コード（`app_clean`）に、実在の欠陥が2つ残っている。** 次の版で直し、テストを足してから測り直す。正解のラベルは変えていない。
- **モデルによる差が大きい。** 同じ指示でも、Opus は Sonnet が見逃す欠陥（TD-03・TD-10 と、参照コードの2つ）を見つける。レビュー担当だけ上位のモデルにする設定は、費用が約4倍でも検討に値する（費用対効果は未計測）。
- **見逃しやすい型は「部品はあるが、値に正しく使われていない」。** 指示を足す方向では、2回試して効果が小さかった（EVAL-02 の SQL の観点・今回の3行）。別の方向（その型のケースを増やして率を測る・レビュー担当のモデルを変える・テストで捉える）を先に試す。

## 限界

- 各ケース3回。題材は Python・SQLite の1つだけ。判定役も Claude（Sonnet の計測では Sonnet、Opus の計測では Opus）。
- テストを取り除く作り方なので、取り除いた箇所は「テストがない」状態になる。レビュー担当が、その箇所のテスト不足を手がかりに欠陥を見つけた可能性がある（テスト不足の指摘は 18〜20件あった）。「テストがあるのに捉えていない」状況より、易しい。

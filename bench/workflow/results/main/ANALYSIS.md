## 読み取り

1. **仕様が明確な課題（spec・archive）では、品質の差は観測されなかった。** spec の必須の失敗は、両条件の6回すべてで同じ2件（`test_unchanged_fields_come_from_the_latest_row` と、同じ欠陥の repro `res_stale_fields`：更新で変えない欄を、最新の行ではなく確認した時点の行から取る）。E-AQDL のレビューはこの欠陥を指摘しなかった。archive は両条件とも全件合格。
2. **E-AQDL の費用は 4〜9倍、時間は 4〜17倍。** パイロット（約6倍）と同じ傾向。
3. **E-AQDL のレビューは、9回すべてで初回に合格し、指摘は軽微な提案だけだった**（修正のループは0回）。今回の課題では、レビューと修正の仕組みが品質に効く場面がなかった。
4. **vague（あいまいな依頼）では、E-AQDL の必須の失敗が平均5件少ない（38 対 43）。** ただし、これは弱い根拠として読む。
   - 隠しテストの多くは、依頼に書いていない規則（入力の境界・移管の組織の境界・監査のマスクなど）を、参照実装の選び方で確かめている。差は「正しさ」より、「参照実装と同じ選び方をした数」を測っている。
   - E-AQDL は、仕様の提示（判断シート）で規則を明文化し、推奨を採った。作成・検索の入力の検証と、移管の組織の境界で、参照実装と一致する回が増えた。
   - 一方で、plain が一度も落とさないテストを E-AQDL が落とした回もある（移管・更新の中の権限の再確認・TOCTOU の repro など。各1〜2回）。改善と後退が混ざっている。
   - plain は3回とも、別のコードで同じ43件を落とした。E-AQDL は 35〜41件とばらついた。
5. **人の返答は、E-AQDL で平均1回**（仕様の承認）。plain は質問で止まらず、0回だった。人の手間は、E-AQDL のほうが多い。

## 限界

- 各3回なので、差は傾向として読む（検定はしていない）。
- 課題は1つの小さなライブラリの3通りの使い方だけ。大きなコードベース・長い作業・複数人での開発は測っていない。
- 人の役は台本で、仕様の中身を読んで直すことはしない。E-AQDL の、人が仕様を確かめて直せる利点は、この計測では出ない。
- 未マージの #23〜#27 の効果は測っていない。
- 参照実装の残りの欠陥（`sort=[]`・文字列の `version`）は、v2 で直す予定。今回の判定には関わらない。

## 結論

今の main の E-AQDL は、仕様が明確な小さな課題で、Sonnet の通常の Claude Code と同じ品質を、4〜9倍の費用で出した。あいまいな依頼では、仕様を明文化することで、隠しテストとの一致が少し増えた（必須の失敗 43 → 38）。ただし、後退した回もあり、決定的な差ではない。品質の向上をうたえる結果ではない。

- レビューで見つかるべき欠陥が実際にある課題（今回の spec の `res_stale_fields` のような欠陥）で、レビューの検出の差を見る。
